# ADR 0011: one platform admin password, sourced from Key Vault

Date: 2026-10-22
Status: Accepted

## Context

The POC now has several logins: Argo CD's `admin`, ThunderID's admin console and the four
OpenChoreo portal users it seeds (`admin@openchoreo.dev` and friends), OpenBao's root token.
Each had its own secret: Argo CD's rotated by hand, Thunder's and the users' as plaintext in
the reference values, OpenBao's as the literal `root`. The owner wants one password for every
admin login. Tekton has no login: its dashboard is read-only and not published (ADR 0009).

External Secrets Operator and OpenBao are already on the cluster (ADR 0010). OpenBao runs in
dev mode (in-memory, re-seeded from Git on every restart), so it cannot be the source of a
password that must not live in Git. Entra Workload ID is off (ADR 0004), so authentication to
Azure from pods has to use the node's managed identity.

## Decision

1. **Azure Key Vault `kv-cloudinfra-poc` is the source** (`live/azure/poc/35-secrets`,
   `modules/azure/keyvault`): RBAC authorisation, firewall default-deny with the operators'
   egress and the cluster's egress IP allowed, soft delete 7 days, no purge protection. One
   secret, `platform-admin-password`, generated by `random_password` (24 chars). Cost:
   effectively zero (standard tier bills per 10k operations; External Secrets reads hourly).
2. **External Secrets reads it with the kubelet identity** (`ClusterSecretStore/azure-keyvault`,
   `authType: ManagedIdentity` over IMDS; the identity has Key Vault Secrets User). No
   credential is stored in the cluster for this.
3. **Per-service delivery, in Git without secrets** (`gitops/platform/platform-secrets`):
   - Argo CD: an `ExternalSecret` merges `admin.password` (bcrypt via the template engine's
     `htpasswd`) into the chart-owned `argocd-secret`; Argo CD re-reads it, so rotation lands
     within the refresh interval.
   - ThunderID: an `ExternalSecret` writes `thunder/platform-admin`; the chart's
     `setup.admin.passwordRef` points at it for Thunder's admin console, and the bootstrap
     users use `{{ .ADMIN_PASSWORD }}`, which Thunder resolves from the setup job's environment.
4. **OpenBao's root token is not synchronised.** It is a token, not a user password; the
   instance is dev-mode and re-seeded from Git. It stays `root` and is documented as such
   until OpenBao leaves dev mode.

## Consequences

- One place to rotate: `az keyvault secret set --vault-name kv-cloudinfra-poc --name
  platform-admin-password --value ...` (or taint the `random_password` and apply). Argo CD and
  Thunder's admin console pick it up within an hour; the four seeded OpenChoreo users do
  not: Thunder seeds them once, so re-run its setup job (`kubectl -n thunder delete job
  thunder-setup`, then sync) or change them in Thunder's console.
- The generated password is in the `35-secrets` state file (storage account, Entra-only,
  allowlisted; ADR 0009) as well as in the vault. Acceptable for the POC; a production
  setup would generate the secret outside the state (e.g. `az keyvault secret set` only).
- A cluster recreate changes the kubelet identity and the egress IP: re-apply `35-secrets`
  after `20-cluster` (runbook) or External Secrets cannot reach the vault.
- Reading the password needs an allowlisted egress and Key Vault Secrets Officer/User; the
  deployer gets Officer from the stack. The `read_admin_password_command` output says how.
- Argo CD's `admin.passwordMtime` is left as is; sessions issued before a rotation stay valid
  until they expire.
